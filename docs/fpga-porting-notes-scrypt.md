# Porting notes: scrypt on the hcfpga framework

scrypt (`SCRYPT:N:r:p:salt:key`, hashcat mode 8900) is the fifth algorithm on the shared FPGA template (`src/fpga/common`, `src/bridges/fpga/hcfpga_bridge.c`) and the second on its `--core custom` path, ported with the LiteX hashcat Guide's `AGENTS.md`. These notes follow the earlier ports' (`docs/fpga-porting-notes-md5crypt.md`, `-sha256crypt.md`, `-descrypt.md`, `-sha512crypt.md`): what was ported, the steps in order, what was generic and what scrypt forced, the layouts, every snag, the proofs and what is not done. The design is described in `src/fpga/scrypt/README.md`, its sources in `src/fpga/scrypt/PROVENANCE.md`.

Result: hash mode 98900 (bridge `fpga_scrypt`) cracks scrypt with r = 1, p = 1 and N up to 32768 through hashcat's litexbone transport against a Verilator simulation of a LiteX board, over UARTBone and Etherbone, with the self-test on. `tools/test.py -m 98900 -P` passes with `HCFPGA_TEST=1`. The core is LiteX-Scrypt's unit, which is not one of John the Ripper's; its full mode, the one hashcat needs, had never run and computed no correct key: three fixes in the unit made it agree with Python's `hashlib.scrypt`. The template, bcrypt's files and the other algorithms did not change. No bitstream has been built for a real board.

**Layout changed after these notes.** The template they describe was replaced by hashcat's documented layout. `src/bridges/bridge_fpga_scrypt.c` is one complete bridge, upstream's `bridge_fpga_bcrypt.c` with scrypt's specifics (`diff` the two), in place of a hook file on the shared `src/bridges/fpga/hcfpga_bridge.c`; and `src/fpga/scrypt/` carries its own copies of the shared RTL, bench, wrapper base and simulated board (`src/fpga/scrypt/hcfpga_sim.py`, without `--algo`) in place of `src/fpga/common/`. The template and the scaffold moved to the LiteX hashcat Guide (`template/`). The paths and hook names below are as they were when the notes were written. On the new layout, the bench, the example hash with the self-test on over UARTBone, `test.py` and the injected-failure row were rerun and passed.

## 1. What was ported

LiteX-Scrypt (the repository owner's own design, built after John the Ripper's ZTEX designs) has the same three layers as JtR's:

| Layer | LiteX-Scrypt files | Kept? |
|---|---|---|
| Computing unit: input FIFO, PBKDF2-HMAC-SHA256 (an iterative SHA-256 core), ROMix with the V table in block RAM, BlockMix, Salsa20/8, the 2-bit serial output | `scrypt/{scrypt_unit,pbkdf2_sha256,hmac_sha256,sha256_core,romix,v_table_bram,blockmix,salsa20_8}.v`, `scrypt.vh`, `main.vh`, `util/fifo_sync.v`, `util/log2.vh` | yes, with full mode fixed |
| Arbiters and comparator, after JtR's | `arbiter_tx.v`, `arbiter_rx.v`, `comparator.v`, `scrypt_cmp_config.v`, `scrypt_axis_8b.sv` | no, replaced by an engine and the template's JtR collector |
| Packet layer and LiteX shell | `pkt_comm/`, `gateware/*.py`, the sim and board targets | no, replaced by hcfpga's records and transports |

The unit has two modes. SMix-only (`FULL_MODE` 0) takes PBKDF2's 128 r-byte output and returns ROMix's, so the host computes both PBKDF2 calls; the old LiteX port ran only this mode. Full mode (`FULL_MODE` 1) takes the password and returns the 32-byte derived key. hashcat's records decide: the H2C record carries a password of at most 255 bytes and the C2H record at most 24 digest bytes, so SMix-only (128 r bytes in and out) does not fit and full mode does. Full mode's PBKDF2 works on 128-byte blocks, so the device computes r = 1, and one SMix, so p = 1.

## 3. Generic versus scrypt-specific

| Piece | As the template has it | Changed for scrypt, and why |
|---|---|---|
| H2C record | bcrypt's, through `hcfpga_h2c_intake.v` | `len` limit 64; the intake's `hold` is driven by the engine, not tied low: a started unit packet is always finished |
| Engine | the custom scaffold's one-candidate stub | replaced: a transmitter building LiteX-Scrypt's packet (44 configuration bytes, the key zero filled to 64, 8 ID bytes, an end byte) one byte every other cycle, `NUM_CORES` units, `hcfpga_gen.v`, and the shared `hcfpga_jtr_unit_collect.v` with `RESULT_LEN` 32 |
| Generation | `hcfpga_gen.v` for cores without a reset | used: the units cannot be reset |
| C2H record | bcrypt's | digest is the derived key's bytes 0..15 at 4..19, hashcat's `digest[0..3]` little-endian, no `digest_from_c2h`; core_id is the unit |
| CSR block | the shared registers, extras from 0x3c | `salt_len`, `salt4..7` (salts up to 32 bytes); `iter_count` is N |
| Identity | `cores=` | counts units; grain 1 per unit |
| Bridge | `hcfpga_bridge.c` | the hook values, `config_extra`, `salt_check` (r, p, N a power of two) |
| Module | the scaffold's bridged copy of module_08900.c | limits (password 64, salt 0..32, N 2..32768, r = 1, p = 1), an example hash with r = 1, `KERN_BITS`/`module_kern_bits` and `scrypt_common.c` out |
| Kernel | the scaffold's pass-through | none |
| Test module | the scaffold's copy of m08900.py | N = 16, r = 1 by default; `maxmem` with room for OpenSSL |
| Template, transports, bcrypt, the other algorithms | | none |

## 4. Layouts

H2C record, unit packet, unit output, C2H record and registers: `src/fpga/scrypt/README.md`. Unit timing, from the bench of the unit alone and the datapath bench: a candidate takes about 63 cycles per step of N (two BlockMix calls of two Salsa20/8 calls each) plus about 1800 cycles for PBKDF2 (4 + 2 HMACs of 66-cycle SHA-256 blocks) and the packets: 1921 cycles at N = 2, 2803 at N = 16, about 66,000 at N = 1024, 2,066,179 at N = 32768. The transmitter's 118 writes take 236 cycles, the result 162.

## 7. Not done

- No real board. The units run at one clock here. `N_LOG2_MAX` 15 is a 4 MiB V table per unit, more block RAM than most FPGAs have for even one unit; a board build picks a smaller `N_LOG2_MAX` (and the module's `FPGA_ITER_MAX` with it), or the external V table (`V_TABLE_EXTERNAL` 1, LiteX-Scrypt's DDR3 option), which this port does not wire.
- Two upstream constructs a synthesis tool may refuse at `R` 1 are left as Verilator takes them (`PROVENANCE.md`, "Left as upstream wrote it"): `blockmix.v`'s `round_cnt[0:1]` and `romix.v`'s out-of-range Integerify arms.
- r > 1 and p > 1. The unit's ROMix takes r up to its `R`, but its PBKDF2 is built for 128-byte blocks; a device for mode 8900's usual r = 8 needs a PBKDF2 over 128 r bytes and an output of the first 16 key bytes, and p > 1 needs p SMix calls per candidate.
- The SMix-only path's `romix_start` is held high until `done` as PBKDF2's start was; hashcat does not use that mode, so it is neither fixed nor checked.
- No wave model: hashcat autotunes, and the batch timeout uses 1000 cycles per step of N per wave.
- The imported LiteX-Scrypt files keep their comments as written, em dashes included (13 in 6 files); the import is verbatim.
